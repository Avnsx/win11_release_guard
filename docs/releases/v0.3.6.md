`0.3.6` keeps the dashboard baseline-update notice's security classification
working during Microsoft-side feed lag. In July 2026 the live dashboard showed
"Security classification is unavailable from the checked enrichment source."
for the new 25H2 baseline 26200.8875 / KB5101650 because Microsoft's Update
History Atom feed had not yet published the Patch-Tuesday article, even though
MSRC CVRF data for the month was already public. The generator now closes that
gap. The release also surfaces previously silent enrichment failures as
warnings and moves the audited `actions/checkout` pin to v7. No signed verdict,
`required_baseline_build` selection, `/api/v1` contract, Source Diagnostics
issue-sync rule, WUA-secondary behavior, or the 14-day baseline-update notice
window changed.

## MSRC Month Fallback During Atom Feed Lag

The active baseline-update notice previously derived its security label only
from an Atom-linked Microsoft Support article (with MSRC joined via the Atom
entry's month). When the Atom feed lagged Patch Tuesday, no Support URL or MSRC
month was derivable, so the notice degraded to
`security_evidence_source: unavailable` until Microsoft published the entry.

Now, when the baseline record has no Atom published/updated dates, the
generator derives the MSRC CVRF month from the Release Health baseline date
(for example `2026-07-14` to `2026-Jul`), fetches MSRC CVRF for that month, and
joins the baseline KB with the existing exact-KB-token rule. Security is then
credited to MSRC (`security_evidence_source: msrc_cvrf`) without waiting for
the Atom entry. No Support article is fetched or synthesized in that case —
Atom remains the only Support-article discovery path, so
`support_article_validation_status` honestly stays `unavailable`. The fallback
applies only to the active baseline-notice record; release-history enrichment,
`latest_observed_build`, and baseline selection are untouched.

Deployed proof: the live feed regenerated the same day showed the July notice
flip from the neutral wording to "MSRC confirms it as a security update" with
`security_evidence_status: trusted`.

## Enrichment Failures Are No Longer Silent

* If the fallback (or any) MSRC CVRF fetch fails, the standard
  `msrc_cvrf_enrichment_unavailable` warning event now fires for that month and
  the notice keeps the neutral wording.
* A baseline record with a real Atom-linked Support article whose fetch fails
  now emits the standard support-enrichment event instead of being suppressed.
  Baseline records with no support URL stay quiet as before, because nothing
  was attempted.

## Actions Pin Audit

Dependabot PR #10 moved `actions/checkout` to `v7` in every workflow; the
action-version audit tool, its tests, and the AGENTS.md audited list moved in
the same change so the pinning gate stays in lockstep. All other pins are
unchanged.

## Test Coverage Added

* Atom-lag fallback path: MSRC month fallback with trusted classification when
  MSRC responds; honest `unavailable`/`unknown` plus the
  `msrc_cvrf_enrichment_unavailable` warning when the fetch fails; a forbidden
  support fetcher proves no Support article is fetched in either case.
* Baseline support-article fetch failure now surfaces the standard enrichment
  event.
* (Since v0.3.5 on main) `tests/test_no_timebomb_policy_dates.py` guards
  against absolute `generated_at_utc` dates on the real wall-clock path.

## Unchanged Verdict Boundaries

- Signed public policy JSON plus detached signature remains the compliance verdict authority.
- Local Windows labels, WUA, Panther/setup logs, DISM, Event Logs, and Source Diagnostics remain diagnostic evidence.
- 25H2 remains the existing-device broad-fleet target.
- 26H1 remains excluded for existing-device targeting.
- `/api/v1` policy, signature, and manifest aliases stay backward-compatible.
- Notice Source Diagnostic events remain dashboard-only and are not GitHub-Issue-syncable.
- The baseline-update notice is informational dashboard output only, visible for 14 days.
